File formats (evidence)
  • Neither public repo stores machine state in TOML or YAML. paperclip keeps tickets in Postgres jsonb and config in JSON; deepseek-harness keeps sessions in JSONL and config in YAML (inherited from its framework, never argued against TOML).
  • Both use markdown + YAML frontmatter for human-authored things (agents, skills, company packages). paperclip's reason: markdown is canonical, human readable, git-native.
  • YAML has no stdlib parser in Python. paperclip hand-rolled a subset parser (its own plan admits it is ad hoc); deepseek-harness depends on js-yaml and yaml.
  • TOML: read-only stdlib parser (tomllib, Python 3.11+, you have 3.14), no writer. parse-then-dump loses comments, so you need closed emitters per record kind. lc-wms does this (ticket_toml.py, dumps_* in trackers.py). control-center hand-rolled a parser (tomlio.py) with real pain: trailing comments kept inside values, single-quoted strings keep quotes, inline tables returned as raw strings, nested dicts silently stringified, comments lost on rewrite, stale lock after a crash blocks for 5 s.
  • Versioning: deepseek-harness uses one integer version, adjacent upgraders, and refuses files newer than the reader. paperclip uses zod schemas, unknown keys pass through, and a malformed config is copied aside before repair.
  • Validation: lc-wms has the best pattern for this project: a data file (ticket-layout.toml) describing required files and patterns, a validator, and hooks (PostToolUse exit 2, pre-commit, CI).
Scaffolding and ticket pages (evidence)
  • No repo has a workspace generator. control-center kickoff creates a ticket from 13 templates but shells out to PowerShell 5.1; lc-wms kanban new is pure Python. paperclip company-creator is an LLM procedure, not code.
  • Best scaffold pattern found: paperclip llm-wiki ships a static template tree plus a validator listing required dirs and files; deepseek-harness claims the target directory exclusively and fails if it exists; paperclip onboarding assets fill a few named {{vars}} by plain string replace.
  • Workspace file: lc-wms commits a template catalog (shoplc.code-workspace.template.json, 20 folders) and gitignores the per-machine copy; paths differ per machine. control-center has a one-folder workspace file that no code reads, and its README names a different file (drift).
  • Per-ticket HTML already exists in lc-wms: kanban brief {T} (.kanban/core/brief.py + brief.html shell) writes architecture/{T}-brief.html, and kanban serve serves /ticket/{T} live with a 3 s stamp poll. Sections: header chips, Frame, Current state, Rules and AC, Plan, Workflow (Mermaid), Hand-offs, Decisions, Risks, Bugs, Todos, Tests, Open items. Markdown is rendered by a stdlib subset md_to_html.
  • control-center has no per-ticket page, only a drawer (fields, trackers, artifact names and sizes, no decisions section) and a static export of the whole SPA board.
  • Caveats to avoid: lc-wms writes are not atomic and only guarded by an in-process lock; its Mermaid loads from a CDN so pages break offline; the two repos name their artifacts differently (spec/plan/tasks vs requirements/analysis/decision-log), so our schema must be chosen, not inherited.
